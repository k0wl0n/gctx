# Phase 1.2: Remove Auto-Save Flag - Always Auto-Authenticate on Create - Research

**Researched:** 2026-04-01
**Domain:** Go CLI flag removal, Cobra command flags, internal refactoring
**Confidence:** HIGH

## Summary

This phase is a focused internal refactoring of a Go CLI tool. It removes the `--auto-save` boolean flag from the `gctx create` command and hard-codes `true` as the value passed to `CreateAccount()`, making auto-authentication the only behavior on account creation. There are two sub-decisions: whether to also remove the `autoSave bool` parameter from `manager.CreateAccount()` (Option 2b — clean removal) or keep the signature and always pass `true` (Option 2a — minimal change).

The codebase uses `github.com/spf13/cobra v1.10.2` for CLI parsing. The change touches exactly two files: `cmd/create.go` (definitely) and `pkg/manager/manager.go` (optionally). The `autoSaveFlow()` method in manager.go already handles the full authentication flow — nothing new needs to be built. The conditional branch in `CreateAccount()` that handles the `autoSave == false` case (printing manual instructions) becomes dead code and should be deleted.

**Primary recommendation:** Remove `autoSave bool` from both `cmd/create.go` AND `pkg/manager/manager.go`. Eliminating the parameter entirely (Option 2b) is cleaner than keeping a parameter that is always `true`. Delete the manual-instruction branch in `CreateAccount()` and update `SetProject()` error handling since the `autoSave` guard around that error path will no longer be needed (it should always warn and proceed, since authentication always follows).

### Pattern 1: Cobra Flag Registration via `init()`

**What:** Cobra flags are registered in `init()` functions in each command file. Removing a flag means deleting both the package-level `var` and the `init()` call.

**Current code in `cmd/create.go`:**
```go
// Source: cmd/create.go (read directly from source)
var autoSave bool

func init() {
    createCmd.Flags().BoolVar(&autoSave, "auto-save", false,
        "Automatically run auth and save credentials")
}
```

**After change:** Both the `var autoSave bool` declaration and the entire `init()` function body (or the whole `init()` if it has no other registrations) are deleted. The `RunE` call changes from `m.CreateAccount(args[0], args[1], autoSave)` to either `m.CreateAccount(args[0], args[1])` (Option 2b) or `m.CreateAccount(args[0], args[1], true)` (Option 2a).

### Pattern 2: Removing a Boolean Parameter from a Function (Option 2b)

**What:** When a boolean parameter is always one value, the parameter and its conditional branches should be deleted. In `manager.go`, `CreateAccount()` has two branches on `autoSave`:

1. `if autoSave { ... warn on SetProject error ... }` vs `return err` (lines 87-91)
2. `if autoSave { return m.autoSaveFlow(name) }` + manual-flow print block (lines 108-118)

**After Option 2b:**
- Function signature: `func (m *Manager) CreateAccount(name, projectID string) error`
- `SetProject` error path: always warn and proceed (since auth always follows)
- `autoSaveFlow()` is always called — remove the conditional
- The manual-instructions `fmt.Println` block is deleted

### Anti-Patterns to Avoid

- **Keeping a dead parameter:** Don't leave `autoSave bool` in the function signature and always pass `true`. It misleads future readers into thinking the flag could be `false`.
- **Forgetting the `Example:` field in the Cobra command:** The current `Example` block in `createCmd` still documents `--auto-save`. It must be updated to remove that example, otherwise `gctx create --help` shows a non-existent flag.
- **Orphaned `var autoSave bool`:** Leaving the package-level variable without deleting the `init()` registration compiles fine but creates a dead variable. The Go compiler will warn if it is unused in a non-`_` assignment, but Cobra's `BoolVar` writes to it so it technically is "used." Don't leave it.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Removing a CLI flag | Custom flag-parsing wrapper | Just delete the Cobra `Flags().BoolVar` call | Cobra handles all flag cleanup automatically when the registration is removed |
| Backward-compat shim | A hidden/deprecated flag that still exists | Full removal | No known external callers; this is v0 CLI; no shim needed |

**Key insight:** This is a deletion task, not a build task. The only risk is leaving behind dead code or stale documentation strings.

## Common Pitfalls

### Pitfall 1: Stale `Example:` Block in Cobra Command

**What goes wrong:** `createCmd.Example` still contains `gctx create my-account my-project-id --auto-save`. After the flag is removed, running `gctx create --help` shows an invalid example that confuses users.

**Why it happens:** Code reviewers focus on functional code, not documentation strings.

**How to avoid:** Update `Example:` in `createCmd` to only show `gctx create <account> <project>` without the `--auto-save` variant.

**Warning signs:** `gctx create --help` output references `--auto-save` after the change.

### Pitfall 2: Incorrect Error Handling for `SetProject` After Removal

**What goes wrong:** In `CreateAccount()`, the `SetProject` error is currently swallowed (with a warning) only when `autoSave == true`. If Option 2b is used and the condition is deleted, the error handling must be consciously chosen — not accidentally left as a hard `return err`.

**Why it happens:** Mechanical deletion of the `if autoSave { ... } else { return err }` block without thinking about which branch survives.

**How to avoid:** Keep the "warn and continue" branch (the `if autoSave` body), because authentication always follows and will set the project. The `return err` (else branch) is the one that gets deleted.

**Warning signs:** `gctx create` returns an error about project permissions before running authentication.

### Pitfall 3: Forgetting to Rebuild the Binary

**What goes wrong:** The existing binary was built 2026-01-05 and is stale. After making source changes, the old binary is tested and the change appears to have no effect.

**Why it happens:** The binary is committed or installed in PATH from a prior build.

**How to avoid:** After source edits, explicitly run `go build -o gctx .` (or `task build` per `Taskfile.yml`) and verify the new binary is used.

**Warning signs:** `gctx create --auto-save` still appears to work (accepts the flag) after the change is made.

### Pitfall 4: `init()` Function Has Only One Registration

**What goes wrong:** If `init()` in `create.go` has only the `autoSave` flag registration, deleting the `BoolVar` line leaves an empty `init(){}`. This compiles fine but is dead code noise.

**How to avoid:** Delete the entire `init()` function if no other flags are registered there (confirmed: `create.go`'s `init()` only registers `--auto-save`).

```go
// After change — autoSave param removed, always runs autoSaveFlow
func (m *Manager) CreateAccount(name, projectID string) error {
    configName := fmt.Sprintf("%s-config", name)

    if err := gcloud.CreateConfig(configName); err != nil {
        return err
    }
    fmt.Printf("Created gcloud configuration: %s\n", configName)

    if err := gcloud.ActivateConfig(configName); err != nil {
        return err
    }

    if err := gcloud.SetProject(projectID); err != nil {
        // Auth always follows, so warn and continue
        fmt.Printf("Warning: Failed to set project ID (%v). Proceeding to authentication...\n", err)
    } else {
        fmt.Printf("Set project: %s\n", projectID)
    }

    account := &config.Account{
        Name:       name,
        ConfigName: configName,
        ProjectID:  projectID,
        CreatedAt:  time.Now(),
    }
    if err := m.config.AddAccount(account); err != nil {
        return err
    }
    fmt.Printf("Account '%s' added to configuration.\n\n", name)

    return m.autoSaveFlow(name)
}
```
